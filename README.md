# llm-meeting-review

Контроль качества встреч отдела продаж на LLM: запись встречи превращается в разбор по чек-листу, где на каждый пункт стоит дословная цитата с таймингом, а стоимость каждого разбора известна до копейки.

Это чистая переработка конвейера, который несколько месяцев работает в бою в компании с отделом продаж на 10 человек. Данных компании и клиентов здесь нет, чек-лист в репозитории учебный.

**Цифры из эксплуатации:** 300 встреч в месяц, 100 % покрытие вместо 1–2 % при ручном прослушивании, около 26 ₽ за разбор, весь бюджет около 7 800 ₽ в месяц при согласованных 10 000. Внешний подрядчик по контролю качества больше не нужен.

## Как устроено

```
запись (mp3/mp4/ссылка)
   │
   ▼
Deepgram nova-3 ── диаризация ──▶ транскрипт с ролями МЕНЕДЖЕР / КЛИЕНТ
   │
   ▼
обезличивание: телефоны, почта, карты, имена с падежами ──▶ [КЛИЕНТ], [ТЕЛЕФОН]
   │
   ├──▶ слой «код»: доля речи, вопросы, монологи,
   │    обязательные и запрещённые формулировки (регулярки)
   │
   └──▶ слой «модель»: Claude, structured output по чек-листу,
        на каждый критерий цитата
            │
            ▼
        проверка цитат: ищем цитату в транскрипте, ставим тайминг;
        «выполнено» без найденной цитаты ──▶ «неясно»
            │
            ▼ (если остались «неясно» и задана вторая модель)
        второе мнение более сильной моделью только по спорным критериям
   │
   ▼
отчёт: Markdown для руководителя, JSON для систем, строка CSV в сводку,
стоимость из usage API, сводка в Telegram
```

Три правила, на которых всё держится:

1. **Цифры считает код, смысл оценивает модель.** Доля речи, количество вопросов, наличие обязательных фраз считаются регулярками. Чем больше объём, тем сильнее хочется верить цифрам, поэтому их не должна выдумывать модель.
2. **Нет цитаты, нет вывода.** Модель обязана привести дословную реплику. Код ищет её в транскрипте с нормализацией. Если цитата не нашлась, статус «выполнено» понижается до «неясно», и это видно в отчёте.
3. **Каждый запрос имеет цену.** Стоимость считается из `usage` ответа с учётом кэша и пишется в отчёт. Правила и чек-лист лежат в кэшируемом префиксе, транскрипт после него.

## Запуск

```bash
pip install -e .
export DEEPGRAM_API_KEY=...
export ANTHROPIC_API_KEY=...

# всё сразу: транскрибация и разбор
meeting-review run meeting.mp3 --checklist checklist.json --out out/meeting.md \
  --names "Иван=КЛИЕНТ,Мария=МЕНЕДЖЕР,Ромашка=КОМПАНИЯ" --csv out/summary.csv

# по шагам
meeting-review transcribe meeting.mp3 --out out/meeting.json
meeting-review metrics out/meeting.json --checklist checklist.json      # без обращения к модели
meeting-review review out/meeting.json --checklist checklist.json --out out/meeting.md
```

Параметры разбора:

| Параметр | Что делает |
|---|---|
| `--model` | модель первого прохода, по умолчанию `claude-opus-5-5` |
| `--effort` | глубина рассуждения `low … max`, по умолчанию `medium` |
| `--second-opinion-model` | вторая модель для спорных критериев, например `claude-opus-5-5` поверх `claude-sonnet-5-5` на потоке |
| `--names` | имена для обезличивания; русские падежи учитываются по основе слова |
| `--manager-speaker` | номер спикера менеджера, если эвристика «менеджер говорит первым» ошиблась |
| `--csv` | сводная таблица, по строке на встречу |
| `--telegram` | сводка в чат, нужны `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` |

Курс для перевода в рубли берётся из `USD_RUB` (по умолчанию 90).

## Чек-лист

Файл JSON, пример в [checklist.example.json](checklist.example.json):

- `company_context`, `meeting_goal`: контекст для модели;
- `criteria`: список `{id, title, description}`, модель заполняет каждый;
- `required_phrases`, `forbidden_phrases`: регулярки для слоя «код», модель их не видит как задачу, только как готовые цифры.

В бою чек-лист приходит из секрета, в репозитории его нет.

## Что получается

Пример отчёта на синтетическом транскрипте: [examples/sample_report.md](examples/sample_report.md). Фрагмент таблицы:

| Критерий | Статус | Время | Цитата |
|---|---|---|---|
| Боль сформулирована | ✅ | 01:20 | Менеджеры сливают заявки. Приходит сто лидов в неделю, до договора доходят пять. |
| Цена бездействия | ❔ | | Менеджер не спросил, что будет, если ничего не менять. |
| Цена названа | ✅ | 07:10 | Стоимость программы четыреста пятьдесят тысяч рублей за три месяца… |

## Как выбиралась модель

Перед запуском четыре модели прогнаны на 20 эталонных встречах с ручной оценкой руководителя продаж. Сравнивались доля совпадений по критериям и цена за разбор. Итог: дешёвая модель на поток, дорогая на спорные критерии. В коде это `--model` плюс `--second-opinion-model`: вторая модель вызывается только если после проверки цитат остались критерии «неясно», и её вердикт берётся только по ним.

## Эксплуатация

В бою конвейер живёт в GitHub Actions по расписанию: берёт новые записи из таблицы, пишет разбор в Google Таблицу и дашборд, шлёт сводку в Telegram. Здесь оставлен [workflow с ручным запуском](.github/workflows/review.yml) по ссылке на запись и тесты на push, чтобы репозиторий работал без чужих таблиц и папок. Секреты: `DEEPGRAM_API_KEY`, `ANTHROPIC_API_KEY`, `CHECKLIST_JSON`, при желании `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`.

## Тесты

```bash
pip install -e .[dev]
pytest -q
```

Обезличивание с падежами, метрики, поиск цитат и понижение статуса, формула стоимости, сборка промпта и схемы, эскалация только по спорным критериям, отчёты. API в тестах подменён, ключи не нужны.

## Ограничения

- Роли назначаются эвристикой: менеджер тот, кто говорит первым. При трёх и больше участниках все, кроме менеджера, считаются стороной клиента.
- Обезличивание по именам требует список имён; имена, которых нет в списке, останутся в тексте. Для полной защиты в бою добавлялся морфологический разбор, здесь он намеренно не включён, чтобы не тянуть тяжёлые зависимости.
- Поиск цитаты работает по нормализованному тексту одной реплики. Цитата, склеенная из двух реплик, не найдётся и понизит критерий, это сознательный выбор в пользу строгости.
